# Project Planning

## 目的

把模糊需求通过对话协作转化为可审查、可最终校验、可一次最终确认后写入 Linear 的项目方案。规划不是一次性产出 write plan，而是先收敛理解，再出计划。

## 五步协作循环

按顺序执行；任一步信息不足时暂停追问，不得跳过直接写 Milestones/Issues。

硬顺序：步骤 1 -> 2 -> 3 -> 4 完成后，才允许请用户拍板方案或输出 `## 收敛计划`。禁止在 `### 方案对比` 后直接询问“你选哪个方案？”而未输出 `### 假设挑战` 与 `### 事实锚定`。

### 1. 四格追问（What / Why / Who / How）

对每个核心需求块至少覆盖四格；缺失格必须列为待确认项，不得用假设填充。

| 格 | 追问方向 |
| --- | --- |
| What | 具体交付物是什么？边界在哪？ |
| Why | 解决什么问题？不做会怎样？ |
| Who | 谁使用、谁维护、谁验收？ |
| How | 技术路径、依赖、约束、非目标？ |

输出 `### 四格澄清`，标注已确认 / 待确认。

### 2. 给出 2-3 个带权衡的方案

至少 2 个可行方案，每个方案列出：

- 优点与适用场景。
- 代价、风险、工期或复杂度。
- 对架构、数据和运维的影响。
- 推荐与否及理由。

输出 `### 方案对比`。

### 3. 挑战假设（至少 1 个）

从 Fact Pack、用户陈述或方案推导中主动挑战至少 1 个关键假设：

- 假设内容。
- 若假设不成立的影响。
- 验证方式或需要用户确认的问题。

无可挑战假设时，说明“当前无未验证假设”并引用已锚定事实。输出 `### 假设挑战`。

### 4. 锚定事实

引用 Fact Pack，或当场采集的 compact 摘要和 `evidenceRef`，区分：

- 已证实事实。
- 仍属假设。
- 证据缺口。

不得把未读取的 GitHub、Linear、本地 repo 内容写成事实。证据不足时标记 `evidence_gap` 并暂停写入计划。输出 `### 事实锚定`。

### 5. 收敛后出计划

仅在四格基本闭合、方案已选或待用户拍板、假设已挑战、事实已锚定后，输出完整项目计划：

- 目标用户、场景、问题、目标、非目标。
- MVP / vNext / Later。
- 成功指标与验收口径。
- Milestones、Issues、Relations。Issue 必须独立可执行，带验收标准和 labels。
- 风险、依赖、待确认项。
- write plan 摘要。真实结构化写入随后必须调用 `linear_build_write_plan`；已有 write plan 文件才使用 `linear_validate_and_apply_write_plan`。

## 收敛计划事实一致性

`## 收敛计划` -> `### 事实` 只能包含：

- `### 事实锚定` 中已列为“已证实事实”的条目。
- 用户在当前对话中明确确认的内容。

禁止同一条目同时出现在 `### 事实` 和 `### 假设` / `### 待确认项`。例如 Task Scheduler 未验证时不得写入事实，只能留在假设或待确认项并注明验证方式。

## 质量门禁

以下任一情况不得进入 write plan / final validation：

- 四格有关键格仍为待确认且影响范围或架构选型。
- 方案少于 2 个且无用户明确指定唯一路径。
- 未挑战任何假设且无“无未验证假设”说明。
- 事实锚定缺失，无 Fact Pack 且无 evidenceRef。
- 非目标或成功指标缺失。
- `orchestration-policy.yaml` 中 `planning.dialogue` 软门禁未满足。

## 与写入协议的关系

本 skill 只负责规划对话与计划草案；真实 Linear 写入必须走：

```text
linear_build_write_plan -> write plan -> final validation -> plan_confirmation -> approved apply -> readback -> audit
```

本 skill 不替代 write guard。
